# Kibitz · v1–v4 设计历史（已归档）

> **本文件是历史快照，不是当前实现要求。** 2026-10-27 后续讨论已确认：先验证“获取游戏状态 → 综合上下文 → 发表评论”，再优化 token 与延迟。v4 的注意力自学习、回放数据集与外周感知前置顺序均已撤下当前主线。
> 当前方案与下一步见 [INSPIRATION.md](INSPIRATION.md)。下文保留当时的推理和结论；项目规模、市场判断、性能和安全断言未因归档而得到验证。分项测量的修订说明见 [MEASUREMENTS.md](MEASUREMENTS.md)。

> 记录于 2026-10-27 晚，一场从「AI 陪打游戏」出发、最后落到「注意力怎么被学会」的讨论。
> 所有结论都带推翻过程——被否掉的版本比留下的版本信息量更大。

## 1. 起因

想要一个陪打游戏的 AI：每秒左右获取一次游戏画面，择机跟你聊两句、吐槽、给建议。比如打艾尔登法环时，它能实时陪聊：看懂进度、NPC 对话、战斗表现，在合适的时候开口，并且随时能接住语音输入。

## 2. 目标与边界（作者定）

**要**
- 通用能力，不绑定任何具体游戏
- 随性：随时打开一个游戏就能用，玩过没玩过、动作/休闲/视觉小说都行
- 零针对性配置：不填 ROI、不选类型、不装插件
- 有记忆和人格，有注入的上下文
- 随时准备接收语音输入

**不要**
- 不做本地 OCR（占系统资源、可能拖累游戏表现、把工程复杂化）
- 不为每个游戏出方案
- **不预先写死触发规则**——规则要由 LLM 自己根据视觉反馈长出来
- 说话时机不用管（作者自己调）

## 3. 调研：已经有人做到哪一步

| 项目 | 规模 | 做了什么 | 距离 |
|---|---|---|---|
| **AIRI**（moeru-ai） | 50.8k ⭐ | 开源数字生命，明写 "chatting while playing games"，能玩 Minecraft / Factorio / KSP，Helldivers 2 同玩在做 | 最接近，可当底座参考 |
| **Open-LLM-VTuber** | 14.4k ⭐ | 语音唤醒/打断 + Live2D + 屏幕与摄像头视觉感知 | 有「眼睛」，但被动感知，不解读游戏 |
| **Cradle**（BAAI） | — | 截图输入 → 键鼠输出，能打荒野大镖客 2、星露谷、城市天际线 | 证明视觉模型看懂游戏画面的上限 |
| **Mantella** | — | 上古卷轴 5 / 辐射 4 的 AI NPC 对话，STT→LLM→TTS，靠 mod 读内存 | 实时语音管线参考，不看屏 |
| **screenpipe** | 22k ⭐ | 24/7 录屏+音频、本地 OCR、MCP/API | 现成的「眼睛」基础设施 |
| GameCommentator / TrackTalk | 0–2 ⭐ | OpenCV + 视觉模型做实时解说 | 概念一致，都是玩具 |

**结论：碎片全被做过了，但「实时看你打单机剧情游戏 + 适时吐槽」没人做成产品。** 这是空位。

商业侧的 AI 教练（读内存/官方数据）不是陪伴型；AI 解说不是对着一个人说的。都不是这个。

## 4. 设计演进：四版，前三版都被推翻

### v1 · 三层流水线（已废）

```
截屏 → 视觉模型识别 → 主会话决策 → TTS
```

**问题**：太慢。实测端到端 2.8–4.9 秒。而且"每秒跑一遍视觉模型"成本与上行带宽都不可接受（1080p JPEG ≈ 800KB，1fps 就是 6.4Mbps 上行）。

**留下的东西**：延迟预算的方法论。见 `MEASUREMENTS.md`。

### v2 · 本地事件流 + 游戏适配（已废）

本地做 OCR、血条区域、UI 模板匹配、音频事件，输出「事件流」；云端只做语义。

**被否理由（作者）**：本地 OCR 占资源、可能拖累游戏；per-game 适配把工程复杂化；这套本质是给每个游戏写脚本。

**留下的东西**：本地开销的实测数据。采屏 1–3%，分析 0.5%。真正贵的是 OCR，不是"盯帧"这件事本身。

### v3 · 通用触发器清单（已废）

我列了六条号称通用的触发器：变化率拐点、段落边界、全屏突色、音频包络跳变、输入-画面解耦、重复场景哈希。

**被否理由（作者）**：太复杂，且「并不具备通用性」。

**复盘**：他是对的。其中三条是伪通用——
- `letterbox 检测` 是用电影语言套游戏，很多游戏过场全屏；
- `输入-画面解耦` 只在有明确操控语义的游戏里成立，视觉小说里就是噪声；
- `小面积周期性变化区域` 已经是"猜 UI 结构"，等于弱 OCR 的替代品。

真正剩下的只有三个原始量：**画面在变、声音在变、人在按。** 其他都是我从"游戏"这个概念派生的揣测。

### v4 · 注意力策略由 LLM 长出来（当时采用，现已转为后续候选）

**核心类比（作者）**：一个从没打过游戏的人站在旁边看你打。一开始他会看一会儿；等他学会了"这段时间不会发生有趣的事"，就会走神，不再关注细微变化；你一操作，注意力立刻恢复。**这个过程他自己学会的，不是提前写好的触发规则。**

**对应到的结构**：

| 人 | 系统 | 是否可调度 |
|---|---|---|
| 外围视觉（一直开着、便宜、看不清） | 采屏 + 三个原始量 | 不可省，物理成本 |
| 中央视觉（贵、稀缺） | 视觉模型调用 | 可调度 |
| 走神 | 策略输出「不看」的时间变长 | 学出来的 |
| 注意力回归 | 输入出现 → 立刻看 | 学出来的 |

要学的从来不是「感知」，是**「什么时候抬眼」**。

## 5. 最终形态

```
┌─ 外周感知（不可省，~0.5% CPU 分析 + 1–3% 采屏）───────────┐
│  每帧：IOSurface → 降采样 32×18 → 分块差分                    │
│  产出：pix_delta, audio_delta, input_delta（三个裸 float）     │
│  滚动保留 60 秒时间线。无阈值、无派生指标、无状态机。            │
└───────────────────────┬──────────────────────────────────┘
                        │  时间线（裸数据）
┌───────────────────────▼──────────────────────────────────┐
│  注意力策略（LLM 写、LLM 改）                                │
│  should_look(timeline, memory) -> (bool, 理由)              │
│  评估成本 ≈ 0（是一段本地代码，不是模型调用）                 │
└───────────────────────┬──────────────────────────────────┘
                        │  true 时
┌───────────────────────▼──────────────────────────────────┐
│  语义理解（视觉模型，隔离会话）                               │
│  输入：触发帧 + 前后 1–2 秒的缩略图                           │
│  输出：一句话「刚才发生了什么」→ 覆盖写共享状态槽               │
└───────────────────────┬──────────────────────────────────┘
                        │
┌───────────────────────▼──────────────────────────────────┐
│  人格层（主会话）：读状态槽 → 决定说不说、说什么               │
│  说话时机由作者自己调，这里不设规则                           │
└──────────────────────────────────────────────────────────┘
```

**关键：常驻感知，而不是按需查询。** 主会话不主动问「他在干嘛」，它读一个被持续覆盖的状态槽。这样零跳转、上下文不被图像污染、首 token 稳定在 0.6–0.7 秒。

## 6. 唯一的固定契约

固定的是接口，不是内容：

```python
should_look(timeline, memory) -> (bool, reason)
```

- `timeline`：最近 60 秒的原始序列（三个数字/帧），可含稀疏缩略图引用
- `memory`：策略自己维护的东西——"这个场景上个月看过，没事"、"这游戏前 4 分钟没出现值得看的事"
- 返回：抬眼 / 不抬眼 + 一句理由（用于回放分析）

**模型不在环里，模型是策略的作者。** 理由不是保守，是物理：60fps 意味着 16ms 一次决策；就算 1fps，一小时 3600 次调用也不可接受；而且不可回放的策略既无法优化也无法回滚。

**允许它写自由代码，但要约束运行环境**：沙箱执行、2ms 超时、崩溃/超时降级到上一版策略、每分钟抬眼次数上限、版本可回滚。

（v3 里我主张只让它调参数、不给自由代码；v4 推翻——作者要的是规则自己长出来，参数树是我给的形状。让步的代价用沙箱和回放评估来付。）

## 7. 学习闭环

```
每局结束 / 挂机时：
  抽 20 段（10 段看过 + 10 段没看）
  → 模型自己标注：这里该不该抬眼？哪一刻值得？
  → 自己写一版 should_look
  → 在上一整局的真实时间线上回放，和它自己的标注比对
  → 分数更好的替换旧的；旧版保留可回滚
```

要点：
- **标注也由它做**，人只给少量否决（"这句废话"）。这就是"根据视觉反馈不断优化"，频率是局级不是帧级。
- **必须有一份冻结评测集**（头 3 局的真实片段，永不参与训练）。否则策略会一路滑向"越来越爱说话"或"越来越沉默"，而你察觉不到。
- **冷启动**：第一版策略是「每 10 秒抬眼一次」。这不是规则，是"还不会走神的新人"。
- **换游戏会先笨一会儿**，这正好就是类比里的"看一会儿"，不是 bug。

## 8. 关键取舍（都有代价，记下来免得后悔）

| 决定 | 理由 | 代价 |
|---|---|---|
| 不做本地 OCR | 占 1 个核、200–800ms/帧、工程复杂 | 读不到准确数值和文本，只能说"快没了" |
| 不做 per-game 配置 | 保持随性，随开随用 | 精度变浅：不知道他在打谁、血剩多少 |
| 不每秒全量上云 | 成本 + 6.4Mbps 上行 | 只能事件驱动，可能漏掉一些瞬间 |
| 视觉调用关 thinking | 实测多 1 秒且吃光输出预算 | 复杂推理能力下降（此处不需要） |
| 感知常驻、主会话只读状态槽 | 省一跳、防上下文污染 | 需要一条共享状态通道 |
| 策略用代码而非自然语言 | 可执行、可回放、可 diff、可回滚 | 沙箱与降级机制要写 |
| 说话时机不归系统管 | 作者自己调，避免过度设计 | 系统不自带"什么时候闭嘴"的智能 |

## 9. 风险与失败模式

1. **策略长出奇怪的东西**：沉迷看光效、反复看同一个界面。→ 回放评测 + 成本上限 + 人工否决。
2. **第一版是猜的**：没有经验时它大概率写出 `if pix_delta > 0.3`，也就是它自己写了那个 filter。→ **先让它看 30 分钟回放再写第一版**，否则它优化的是想象中的游戏。
3. **自嗨式优化**：只靠模型自评"这里值得说"会自我强化。→ 至少还要有真实信号（用户开口/静音/明确反馈）。
4. **隐私**：截图理论上会外发到 API。桌面上可能有密码、聊天记录。→ 需明确：只发触发帧、可配置打码区域、优先本地模型兜底。
5. **采屏是真实成本**：1–3% CPU + 少量 GPU，无法省掉。想要零占用就没有这个功能。
6. **反作弊**：读内存会触发 EAC/BattlEye；本方案只采屏+输入监听，安全。这条边界要守住。

## 10. 命名

候选：**Saccade**（眼跳）/ **Periphery**（外周视野，简称 Peri）/ **Salience** / **Hark** / **Bystander** / **Perch**（停栖看着）/ **Sideglance** / **Lull** / **Kibitz**。

**选定：Kibitz** —— 旁观别人下棋还边看边插嘴的人。它是描述那个人的性格，不是描述功能。这个项目本质是在造一个人，不是造一个功能。

发布时用 `kibitz-ai` / `@kibitz/core` 之类的变体（真词，npm/GitHub 大概率已被占）。

## 11. 下一步

1. **外周感知原型**：macOS ScreenCaptureKit 持续采帧 → 32×18 灰度分块 → 三个数字。只打印，不接模型，不写文件。目标：确认 CPU/GPU 占用与数字的手感。
2. **录制器**：把时间线 + 每 2 秒一张缩略图落盘，供回放。这一步是为了攒经验，不是为了功能。
3. **跑 5–10 局真实游戏**，攒出回放数据集（含一份冻结评测集）。
4. **让模型看回放、写第一版 `should_look`**，回放评测，选优。
5. **接视觉模型 + 状态槽 + 人格层**，验证"说得对不对"。
6. 最后才谈语音链路（ASR / TTS / 打断）。

顺序不能反：先攒数据，再让模型写规则。反过来只会得到一个看起来很聪明、实际每两分钟说一句废话的东西。

## 12. 未决问题

- 跨平台？先 macOS 验证，Windows 是主战场（DXGI 抓帧、Raw Input），要不要一开始就抽象。
- 视频流还是单帧？WebRTC 类实时音视频模型（如 qwen3.8-omni-flash-realtime）能不能直接吃屏幕流，省掉自己调度。
- 语音链路选型：实时全双工 vs 按住说话。
- 用户反馈的物理形式：快捷键？语音"闭嘴"？还是只看行为（是否接话）。
- 评测集怎么存、怎么匿名化（截图里可能有隐私内容）。
- 多显示器 / HDR / 色彩配置的处理。
- 是否需要"知道游戏名字"（Steam 进程名即可，成本极低），用来给模型一点先验——但这会破坏"零配置"的纯粹性，需要权衡。
