## 1. 延迟

### 截图

| 方式 | 耗时 | 备注 |
|---|---|---|
| `screencapture -x -t jpg` 全屏 | **80–150 ms**（5 次：147/98/81/80/80） | 大部分是进程启动 + JPEG 编码 |
| 进程内单帧（ScreenCaptureKit） | 估 20–50 ms | 未实测 |
| 持续流拿单帧 | 估 0–3 ms | 不编码、不落盘，只取 IOSurface 引用 |

### 视觉调用（`deepseek-flash`，输出 JSON 约 30–40 token）

| 输入 | 耗时 | prompt tokens |
|---|---|---|
| 720p（1280×720）非思考 | **1112 / 1304 ms** | 622 |
| 1080p（1920×1080）非思考 | **1015 / 1373 ms** | 1012 |
| 720p 首 token（流式） | **660 / 1033 ms** | — |
| 1080p 首 token（流式） | **971 / 1005 ms** | — |
| 720p + thinking 开启 | **2018 ms**，且 150 token 预算被思路吃光 | 648 |

**样本结论 1**：本批 720p / 1080p 请求耗时接近，但各只有两次完整响应样本，不能推出分辨率不影响延迟，也没有比较状态理解准确率。
**样本结论 2**：这次 thinking 请求耗时更长，150 token 预算不足以完成回答。可作为初版关闭 thinking 的参考，不能据此断言它对所有任务都是负担。

### 旧架构耗时推算（未实测完整链路）

以下沿用旧设计的分项区间，包含未实测的会话冷启动、TTS 和采样等待。它们不是新主流程的延迟承诺。

| 架构 | 分项 | 合计 |
|---|---|---|
| v1 三段式（截图→视觉→决策→TTS） | 0.08–0.15 + 1.1–1.4 + 0.3–0.8(会话冷启动,估) + 0.7–1.3 + 0.6–1.2(TTS,估) | **2.8–4.9 s** |
| v4 状态槽已更新后的文本决策与 TTS | 0.7–1.3 + 0.6–1.2(TTS,估) | **1.3–2.5 s** |
| v4 新事件需先完成视觉理解 | 1.1–1.4 + 0.7–1.3 + 0.6–1.2(TTS,估) | **2.4–3.9 s** |
| v4 新事件再加 1s 采样的平均等待 | 上一行 + 0.5（假设事件相位均匀） | **2.9–4.4 s** |
| 规则/模板兜底（估算） | 预置台词，无模型 | **0.3–0.6 s** |

修订说明：原 v4 表把“状态已经更新”误写为“事件已发生”，漏掉视觉理解；原 `1.3–2.5 + 0.5 = 2.4–3.6` 也存在算术错误。多帧输入与完整调度开销尚未测量。若等候事件发生后的未来帧，还需计入额外等待。

当前初版拟由一次多模态调用完成理解与评论，先输出文字；耗时需在实际主流程中重新测量，不能直接套用上述拆分架构。

TTS 首音、实时 ASR 首字均未实测（估 600–1200ms / 200–500ms）。

## 2. 本地计算

| 步骤 | 实测 | 说明 |
|---|---|---|
| 解码 1080p JPEG + 降采样到 32×18（`sips`，含进程启动） | **25–42 ms** | 几乎全是进程启动；进程内 vImage/Accelerate 估 <1 ms |
| 576 个数差分（纯 Python 循环） | **0.146 ms** | 30fps ≈ 0.44% 单核；原生代码约微秒级 |
| 数据量 | 32×18 = 576 个数 = 全屏 0.028% | 降采样同时完成抗噪（低通滤波） |

**候选原理**：用低分辨率亮度差分表示宏观变化；是否能保留小面积重要变化、辅助选择值得看的时刻，尚未验证。相关注意力方案已移出初版主线。

**待验证的采屏占用**：旧文记录 1080p30 持续采集约 1–3% CPU + 少量 GPU，但未附具体方法与原始记录，暂按待复核参考处理；576 个数差分的耗时不能代表完整采屏与分析链路的占用。

## 3. 历史成本推算（1fps × 1080p，假设汇率 7.1）

以下保留旧版按图像输入 token 与当时单价整理的估算，未包含完整文本上下文、输出、策略学习和语音开销；参数与价格待复核，不是总费用实测。

| 模型 | 单帧图 token | ¥/分钟 | ¥/小时 | 来源 |

| deepseek-flash（直连，闲时） | 1024 | **0.08** | 4.5 | 官方文档 |

| claude-haiku-5.5 | 2765（w×h/750） | 0.13 | 7.6 | 挂牌价 |
| gemini-3.8-flash | ~774 | 0.34 | 20.6 | 挂牌价 |

旧版对事件触发（约 20 帧/分钟、540p）的假设估算为 **¥0.3–4/小时**，尚无实现或实际使用数据支持，不作为当前费用承诺。

**三个成本陷阱**
1. **上下文累积**：图像与文字窗口都会增加消耗。初版保留有限近期帧以验证连续理解，具体窗口与摘要方式后续根据用量和体验调整，不预先强制每轮丢弃所有图像。
2. **分辨率**：本批 1012→622 prompt token 约下降 39%；对不同画面、模型的成本与理解质量影响仍需验证。
3. **本地处理**：像素分析和 OCR 也有资源与维护成本，准确率取决于具体任务。初版按当前边界不做本地 OCR，文字识别能力需在视觉模型中验证，不能预先断言只能模糊表述。

## 4. 当时记录的外部参数（本次未复核）

- DeepSeek 图片输入上限 **1024 token/张**，超出部分被缩放到约 1300×1300 总像素量。
- DeepSeek `deepseek-flash` 单价：输入 $0.15/M（闲）/ $0.30/M（峰），输出 $0.6/M / $1.2/M；峰时为 UTC 01:00–04:00、06:00–10:00 工作日。
- Qwen 系列图片 token 公式：`h × w / (32 × 32) + 2`，单图最大 1600 万像素。
- 原记录称前述参数来自官方文档，Gemini/Claude/GPT 单价来自 OpenRouter 挂牌价；本项目未附原始来源链接，也未逐家核对官网。需在实际选型时重新核验。
